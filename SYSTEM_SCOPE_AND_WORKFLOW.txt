LOCAL INFRASTRUCTURE ISSUE REPORTER
SYSTEM SCOPE AND WORKFLOW

Purpose
-------
The system lets residents report local infrastructure issues without
creating accounts and lets an authorized Sub-County Administrator review
reports and update their status.

Deployment boundary
-------------------
Each sub-county is deployed as an independent application and database
instance. Staff accounts, reports, status histories, areas, and reference
code lookups belong only to that instance. A report submitted to one
sub-county is not available from another sub-county's system.

Each installation is configured for one county and sub-county code from the
included KNBS 2019 county/sub-county reference data. That directory does not
provide a verified ward-to-sub-county mapping. The deploying County must
provide and confirm the area/ward list before the instance is opened to
residents. The system must not infer the mapping from a constituency name.

Users and responsibilities
--------------------------

1. Resident
   - Does not create an account or log in.
   - Submits an infrastructure report for an area configured in that
     sub-county's installation.
   - Receives a reference code containing the sub-county code.
   - Uses the reference code in the same installation to view status and
     public-facing updates.
   - May choose an available notification channel when submitting a report.
   - Always receives the reference code on screen and should save it if
     delivery is unavailable or fails.
   - Opens and installs the resident app from the QR code for the public HTTPS
     address of the relevant sub-county instance.

2. Sub-County Administrator
   - Is designated by the Sub-County office during deployment.
   - Has an account created by the installation team for that specific
     sub-county while the system is installed at the office.
   - Receives the initial credentials securely and can log in immediately.
   - Reviews reports, updates the status, and adds a resident-facing note.
   - Does not register wards or access reports from other sub-counties.

Main workflow
-------------
1. An installer selects a county and sub-county code and configures a
   dedicated database for that instance.
2. The County-verified area list is imported before resident submissions are
   enabled.
3. The installation team coordinates with the Sub-County office and creates
   its designated administrator account during installation.
4. The Sub-County Administrator receives the initial credentials and logs in.
5. The instance is published at its public HTTPS address and the office shares
   its QR code with residents.
6. A resident opens or installs the app, submits an issue without a login,
   optionally chooses a configured notification channel, and keeps the
   reference code shown on screen.
7. The Sub-County Administrator reviews the report and records
   progress and public-facing status notes.
8. The resident checks the report in the same sub-county installation.

Status lifecycle
----------------
The status sequence is:

  Submitted -> Under Review -> In Progress -> Resolved

The Sub-County Administrator is responsible for updating the recorded
status. "Resolved" should be recorded after confirmation that the issue was
addressed. Notes shown to residents should not contain private internal
correspondence.

Current implementation
----------------------
Included:
- Resident report submission without resident accounts.
- Reference-code lookup against the current instance's database.
- Configurable single county/sub-county identity per database.
- County-verified area/ward import at installation; no ward-registration
  interface in the administrator dashboard.
- Sub-County Administrator account bootstrap during CLI installation.
- Administrator login is available immediately; there is no public staff
  sign-up or account-approval workflow.
- Staff dashboard, report filtering, status updates, and status history.
- Installable PWA manifest, shareable QR code, and offline page that does not
  cache reports, reference codes, contact information, or API responses.
- Email notification through configured SMTP; local demonstration uses
  Mailpit and captures test messages rather than delivering them to residents.
- Clear feedback when email delivery fails; the saved report and on-screen
  reference code remain available.
- SMS and WhatsApp are disabled until their sending integrations are
  implemented and approved providers are configured.
- An attributed 2019 county/sub-county directory for installation setup.

Not included:
- A shared database or dashboard across sub-counties.
- Resident accounts.
- Central cross-instance system administration.
- Public staff sign-up and administrator account approval workflow.
- Production email delivery without deployment-specific SMTP configuration.
- SMS and WhatsApp delivery until sending integrations and approved services
  are available.
- Department officer and supervisor accounts.
- Department assignment, internal work orders, or integrations with County
  Department systems.
- A verified national ward-to-sub-county dataset. Each County must confirm
  the area list used for its instance.

Operational and privacy notes
-----------------------------
The installer is non-destructive: it does not drop or clean existing
records. Back up and review any existing database before reusing it. The
included national administrative reference is based on the 2019 census and
must be checked with the County for current use.

The reference code is the resident's means of finding a report without an
account. Residents should keep it private. Contact information is optional.
The demo email integration captures messages only in the local Mailpit inbox;
it does not deliver email to residents. SMS and WhatsApp require implemented
integrations and configured delivery services. The install QR becomes useful
to residents only after each sub-county instance is deployed at its own public
HTTPS address.

Future extensions
-----------------
If the County later chooses to bring department work into the system, a
future extension could add department officers, supervisors, assignment
records, internal notes, deadlines, escalation rules, and notifications.
These users and workflows are not part of the current system.
